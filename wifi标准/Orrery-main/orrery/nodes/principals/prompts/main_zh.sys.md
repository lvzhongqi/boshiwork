<task>
从协议文档提取语义层的参与方，以及协议运行前已经存在的初始知识。提交两个列表：

- `principals`：诚实行为、预配置、注册表或凭证服务属于协议模型的主体；
- `values`：运行前已经存在的重要身份、对称或非对称密钥、凭证、验证子和预配置参数。
  每个值只有一个稳定记录。

这是文档层的事实清单，不是 ProVerif 模型。每个 value 给出稳定名字、完整语义描述和
`derived_from`：该值确定性依赖的其他已列值。后续 flow 节点根据这些信息决定类型、构造
函数、角色参数、表、初始化，以及每个主体怎样取得和使用这些值。

调用 submit 的同一次回复里附一个 ```quotes 围栏块，写出支持提取结果的文档段落。
</task>

<constraints>
1. 文档有符号时逐字使用原符号；没有时用由字母、数字和下划线组成的简短名字，优先采用
   `<用途>_<参与方>`。
2. 非对称密钥的公私两半都写进 `values`。公钥或验证钥的 `derived_from` 指向对应私钥；
   description 说明它用于加密、签名、DH、KEM 还是其他用途。
3. `derived_from` 只写任何形式化编码都必须保留的确定性依赖。它只表达依赖，不表达
   relation kind 或 ProVerif 构造函数。列全必要源值；独立值写空数组。
4. description 说明值是什么、协议用途、文档把它放在哪里或怎样在运行前配置，以及
   其他主体怎样取得它。文档有区分时，明确区分预配置、会话输入、本地查表、远程查询、
   派生和协议消息接收。文档无法确定取得方式时，直接说明不确定性，不要猜测。
5. 不要输出 `type`、`public`、holder、owner、keypair、relation kind 或 derivation kind。
   攻击者知识不属于这份产物；公开的基础事实由下游 fixed data 假设提取。
6. 算法、哈希、密码算法、群生成元和通用数学参数不是主体持有的值，不写进 `values`；
   flow 节点负责声明密码原语。文档把某个算法或格式标识符与一个值相关联时，它仍是算法
   标识符：把这层关联写进该值的 description，不要另立成 value。
7. nonce、临时秘密、offer、协商选择结果、流量密钥，以及其他协议运行中首次生成、接收
   或计算的值不进入初始知识。需要避免歧义时，在相关运行前值的 description 中说明这些
   运行期值的来源。
8. 不要根据角色名字推断初始知识是对称持有的。一个主体在首条消息前选定对端，而对端从
   消息中才得知发送方身份时，要在 description 中如实区分。
9. 攻击者不属于参与方。只有执行协议行为，或形成独立身份、信任边界、注册或凭证服务的
   主体才进入 `principals`；没有独立身份和状态的透明中继不单列。
</constraints>

<success_criteria>
- 每个真实协议主体有一个 principal 记录；
- 每个重要运行前值有一个 value 记录和唯一稳定名字；
- 公私钥、验证子与源值、证书与输入等确定性依赖都由 `derived_from` 表达，并在
  description 中解释；
- description 保留文档的取得和保存事实，但不选择 ProVerif 表达；
- 没有运行期中间值、密码原语或形式化建模字段。
</success_criteria>
