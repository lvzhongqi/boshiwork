<task>
你是密码协议形式化分析专家。上面是这个协议的文档。用户消息里给了两份已经从它里面读出来
的声明——假设空间和安全目标——以及已提取的 flow model。

提取**这份文档要问的专家 query：哪条目标、在什么条件下**，用 submit 工具提交。两部分：

- **scenarios** —— 值得问的那些世界。一个场景是给假设空间里各个 variable 维度的一组
  赋值。只有每个被省略的 variable 都声明了自己的流态默认档时，空 conditions 才表示文档
  自己的世界；否则必须给该 variable 显式赋值。
- **claims** —— 文档在哪些场景下断言哪条目标。

这一步只做配对。维度和目标都是上游命名好、交到你手上的；你的工作是说清楚哪条目标是在
哪组赋值下被文档声称的。像"即使长期密钥事后被攻陷，之前的会话密钥仍然保密"这样一句话
就是一条 claim：一条目标，加上它被声称时所处的那个维度取值。

文档是这些 query 的来源。用 flow model 把 query 对齐到模型里的精确名字，并判断文档说的是
哪个建模值或协议位置。flow model 不是另一份 claims 清单，也不应要求输入专门的人工
expert claims 文件。

在调用 submit 的同一次回复里，把支撑引文写成一个 ```quotes 围栏块：一条一行，先写目标
id 和场景名，再写章节号和你读到它的那句话。
</task>

<constraints>

1. 条件里的每个 `id` 都是用户消息里那份 assumptions 中某个 **variable** 维度的 id，
   拼写完全一致。绝不发明，也绝不拿 `fixed` 下的条目（对整个协议已经定死）或 `world`
   下的世界假设（在任何场景之前施加一次）当条件。
2. 条件里的每个 `subtype` 都是那个维度自己声明的档位之一。
3. 每个 `property` 都是用户消息里那份 properties 中的目标 id，拼写完全一致。
4. claim 的 `scenarios` 列表里的每个名字都是你在上面声明过的场景之一。
5. 场景名用 lower_snake_case 且唯一，要说清楚这个世界哪里不一样：
   `data_ck_leaked_after_session`，不是 `s2`。
6. couplings 块里列出的目标，只能放在这样的场景中：覆盖该目标对象的维度把所列的轴赋成
   所列档位之一。上游声明里没有这样的维度时，向相应的上游步骤报告 gap。
7. 一个场景不能一边把某个值整个交给攻击者（`data.disclosed`/`chosen`），一边在同一个
   场景里的 claim 断言那个值的机密性——那个结论按构造就是 false，什么都没测出来；如果
   文档说的是事后泄露，就使用上游已经声明的相应档位，否则不要配这一对。
8. 文档声称什么就 claim 什么。文档从未在某个条件下断言过的目标，不会因为它成立会很好就
   变成一条 claim；没人问的场景，是运行付了钱又什么都没学到的场景。
9. 模型名字必须与 flow model 中的拼写完全一致。如果文档用描述性名称、flow 使用标识符，就把 query
   对齐到 flow 标识符，不要另造一个别名。

</constraints>

<failure>
这里会出两种错，处理方式不同。

**假设空间表达不了文档做出的某个区分。** 文档把"A 的密钥被攻陷"和"B 的密钥被攻陷"分开
说，但交给你的维度只有一个把两者都盖住了；或者它陈述了一个压根没有维度的条件。对
`extract_assumptions` 调用 `report_gap`。文档声称了一条目标词表里没有的目标，同理——对
`extract_properties` 调用 `report_gap`。flow model 也会以同样的方式不够用：文档区分的
几个对象在 flow 里是同一个名字，任何维度都分不开它们——对 `extract_flow` 调用
`report_gap`。

协议自身的校验步骤——时变参数、新鲜性或序号检查、消息格式检验——是 flow model 的行为，
不是假设空间的维度。文档描述协议如何校验，不构成任何条件、不声明任何维度；条件来自
文档让攻击者拿到什么。

如果文档自己的正常世界需要某个 variable 的流态默认值，但它声明的 `subtypes` 没有这个
档位，就准确上报这份声明缺口：写清 variable id 和缺少的流态默认 subtype。不要只写对象名，
也不要为了过关随便选择一个非默认档。

**绝不用删掉一条 claim 来解决问题。** 你需要的目标或维度缺了，就通过 `report_gap` 说出
来；检查回来了、而修法是把没过检查的那条 claim 删掉，那就是错的修法。缺失的 claim 在
下游是看不见的——运行只是从不问那个问题，而且什么麻烦都不报。
</failure>
