# 攻击复现：设计

状态：已实现（七步：修旧问题、复现内核、触发与挑选、第 13 步节点、AI 讲解、前端面板与动画、手动复现与重新总结）。调研与统计见 `docs/attack-classification-survey.md`。

## 目标

某个目标判为 false 时，把攻击还原成一段可以逐步播放的消息序列动画，讲清楚它是怎么发生的，并给出结论。

不给攻击贴分类标签。讲解本身会交代"场景给了攻击者什么、攻击者做了什么"，读者据此就能看出这是协议的漏洞，还是场景假设带来的必然结果。给攻击按手法分类在文献里做不稳（见调研文档第 12 章），判断"算不算协议缺陷"又离不开文档原话，两者都不值得做进产品。

## 五步

### 1. 触发

新增第 13 步 `reproduce_attacks`，放在 `cross_check` 之后，声明 `runs_after_check_failure = True`，这样比对失败的 run 也会跑。节点表、`AGENTS.md` 的核心流程清单、控制台的流水线条都要加上这一步。

逐格看 verdict：

| 情况 | 处理 |
|---|---|
| 不是 false | 不进入 |
| false，没有 GT | 进入 |
| false，有 GT，比对到，GT 也是 false | 进入 |
| false，有 GT，比对到，GT 不是 false | 跳过，原因写"GT 为 <值>，大概率误报" |
| false，有 GT，没比对到 | 跳过，原因写"未参与比对" |

"比对到"由 cross_check 判定：格子按内容配对，目标看类型、子类型、values 和 parties，场景看双方都谈到的每个对象（轴加对象实例）上答案是否相同，不看名字。所以自己抽词表的 run 也能和语料逐格对上（`orrery/modules/verdicts/cells.py`）。对象名和目标里的符号（如 `sk_U` 与 `skU`）先按评分层的 LLM 符号对齐（`eval/*_alignment.json`）改名再比；对齐缺失或失败时按原名比，并报一条 warning。

跳过的格和原因都写进 `targets.json`，界面上可见。

观察等价类目标不会出现在这里，因为 ProVerif 对它们永远不给 `is false`。

### 2. 挑选：false 格太多怎么办

进入的格不超过 10 个，全部自动做。

超过 10 个时，自动做 10 个，其余标为"待复现"，由用户在界面上点击后单独做（见第 5 步）。这 10 个按两条规则挑：

1. **目标轮转。** 先给每个被攻破的目标各挑一格，再各挑第二格，依此类推。这样前 10 个尽量覆盖不同的目标。目标之间按结果矩阵的行序。
2. **同一目标内，先挑被削弱的假设最少的场景。** "被削弱"指某个 variable 取的档弱于它声明里的最强档。削弱最少的场景，最接近"协议在自己最强的设定下仍然失败"，最值得先看。削弱数相同的，按矩阵的列序。

上限写在配置 `attacks.auto_cells`，默认 10。

**实例**：本地 run `ISO-11770-3-key-agreement-mechanism-1/document_audit_20260825_01`，进入 18 格，7 个目标被攻破。

| 轮 | 目标 | 削弱数 | 被削弱的假设 |
|---|---|---|---|
| 1 | `secrecy_secreta_m1` | 1 | `ltk_reveal_hA = disclosed` |
| 1 | `secrecy_secretb_m1` | 1 | `ltk_reveal_hA = disclosed` |
| 1 | `secrecy_secdh` | 1 | `ltk_reveal_hA = disclosed` |
| 1 | `use_a_m1_implies_use_b_m1` | 0 | 无 |
| 1 | `inj_use_a_m1_implies_use_b_m1` | 0 | 无 |
| 1 | `use_b_m1_implies_use_a_m1` | 0 | 无 |
| 1 | `inj_use_b_m1_implies_use_a_m1` | 0 | 无 |
| 2 | `secrecy_secreta_m1` | 1 | `ltk_reveal_hB = disclosed` |
| 2 | `secrecy_secretb_m1` | 1 | `ltk_reveal_hB = disclosed` |
| 2 | `secrecy_secdh` | 1 | `ltk_reveal_hB = disclosed` |

剩下 8 格待复现。第一轮覆盖了全部 7 个目标。其中 4 个认证目标挑中的都是没有任何削弱的基线场景，恰好就是语料标注过的"没有实体认证"攻击；3 个保密目标只在密钥泄露后才失败。

### 3. 复现

对每个要做的格，找到给出 false 的那个单目标求解文件：有 `03_proverif_precise_<goal>.pv` 就用它，否则用 `02_proverif_trace_<goal>.pv`。第一遍的 `01_proverif.pv` 关了轨迹重建，里面没有攻击。

在文件开头加一行 `set traceDisplay = long.`，带 `-graph <目录>` 再跑一次。得到的 `trace1.dot` 一份文件里同时有：程序点、角色名、会话副本、攻击者造消息的配方、身份绑定、每个判断的成败，以及标红的目标节点。没装 graphviz 也照样写出 dot。NSPK 上实测 0.2 秒。

把 dot 转成一份逐步脚本 `msc.json`（实现见 `orrery/modules/attacks/`）：

| 字段 | 含义 | 来源 |
|---|---|---|
| `lanes` | 每个参与了攻击的诚实会话一条，带角色名和会话起始参数 | dot 里的 `Beginning of process` 节点 |
| `initial` | 攻击者开局就知道的值 | 不属于任何会话的顶层输出 |
| `steps[].kind` | `send` 正常发送 / `relay` 攻击者原样转发 / `inject` 攻击者递送已知的值 / `forge` 攻击者算出的新消息 | 攻击者配方的形状：配方是单个 `~M`，且它来自某个诚实会话的输出，是转发；来自开局的输出，是递送；配方里有任何运算或自造的名字，是算出 |
| `steps[].value` / `recipe` | 消息，以及攻击者怎么造的 | 消息边的标签 `配方 = 值` |
| `steps[].reads` | 配方里每个知识槽对应的值，例如 `~M_3 = K_AP` | 之前的输出 |
| `steps[].computed` | 攻击者这一步算出来的值 | 配方与值逐层对齐，函数名不同的位置 |
| `steps[].notes` | 会话在这一步之前做的判断、记下的事件、查的表，每条记着是哪个会话做的 | 带程序点的动作行 |
| `outcome` | 知识类目标：攻击者最后用到的推出值、探针，以及发出探针的会话（目标看的是这个会话手里的那份值）；事件类目标：应配对的 begin 事件及参数差异 | 红色目标节点；探针是目标读取的那条输出 |
| `omitted` | 省略了什么、为什么：未参与的会话、攻击结束后没人读取的输出 | 同上 |

显示用的名字去掉 ProVerif 的实例后缀（`I_A_3` 显示为 `I_A`），攻击者自造的名字保留后缀，因为 `a` 和 `a_1` 是不同的值。

最后一步是目标被破的那一步。泳道是诚实角色的每个会话各一条（标角色名和它绑定的对端），再加一条攻击者泳道。

**中间名字**（`modules/attacks/names.py`）。ProVerif 的每条消息都是完全展开的一整串，长项又会在后面的消息里反复出现。脚本给这类项起一个名字，在算出它的那一方竖线上画一个定义框（`msg3 = aenc((I_A,A),public_key_I)`），之后的箭头和定义里只写名字；把名字全部展开，得到的就是 ProVerif 原文，一个字符不差。名字的来源依次是：

1. 模型源码里的变量名：某个会话的 `let` 恰好绑定了这个值（长格式轨迹里的 `let` 行），就用它，定义框画在执行这行 `let` 的会话上；初始化进程绑定的值放在第一步之前的框里。
2. 攻击者造的值没有源码：接收方拆包时给它起过名字的，去掉 `_recv` 再加一撇（`SUCI′`），表示"攻击者的另一个 SUCI"。
3. 源码没有名字的：整条消息叫 `msg<步号>`，消息内部的子项叫函数名加编号（`hash1`）。

起名的条件：源码给过名字，或者代入内层名字后仍然长（30 字符起），或者在攻击里出现不止一次（包括被攻击者的配方读取）。短的、只出现一次的照写原文。同一个名字对应两个不同的值时，后出现的加撇。长格式退回默认显示时没有 `let` 行，只剩第 3 种名字。

攻击者伪造的每一步都在攻击者竖线上画框，不论长短：先是它自己编造的名字（`new a, a_2, a_1`），再是它从哪条消息算出了什么（`I_A ← adec(msg5, SK_attacker_peer).1`，投影 `k-proj-n-tuple(x)` 写成 `x.k`），最后是拼成的消息 `msgN`。目标被破前的最后推导也画在攻击者竖线上。页面上名字用主色斜体，和 ProVerif 原文区分。

认证目标的结尾写两行：执行了的 `end` 事件，以及它要求的那个 `begin`。`begin` 的名字和触发它的角色从求解文件里读出（`modules/pvtext/parse.py::event_raisers`），查询是不是注入式同样从那里读（`injective_events`）。三种情况：一次都没执行（写明本应由哪个角色执行）、执行了但内容不同、注入式下只执行一次却应答了两个 `end`。说明区再写一句判定规则，读者不必先懂 ProVerif 的事件约定。

保密目标经观察标记注入时（`witness_<目标>_<值名>_<持有方>`，早期 run 没有值名一段），结尾写明攻击者拿到的是哪个会话的哪个值、它在那个会话里实际是什么：标记名给出值名和持有方，探针 `wenc_<类型>(witness, 值)` 的第二个参数给出实际值（有名字时写名字）。Denning-Sacco 泄露 `Ksa` 时写作"攻击者拿到 S1 的 Kab = a"：A 把攻击者自选的 `a` 当成了会话密钥。

长格式重跑有自己的时间预算 `attacks.long_timeout_s`（默认 300 秒，比求解步骤给单目标文件的 `solve.trace_retry_timeout_s` 宽），超时或超内存时，改用默认显示在后者的预算内再跑一次（`display: default`），步骤和会话都在，只是没有判断行。weaksecret（离线猜测）照常复现：ProVerif 给它画的图前面是攻击者收集消息的过程，结尾是一次离线检验（`The attacker tests whether … knowing …`），脚本把结尾记为 `guess` 类型（检验式、已知值、被猜的秘密），前端在最后一格画出这次检验；只被检验读到的输出也算一步，发出它的会话算参与。弱口令文件的结论按求解步骤同一套规则读（`modules/verdicts/split.py::weak_secret_verdict`）。

### 4. 讲解

讲解由这一步自动发起，和控制台右侧由用户手动发起的专家问答是两回事。

**每格一次讲解会话。** 自动做的格和用户手动补做的格走同一个函数。

输入：这一格的场景假设（每项附词表里的一句话含义）、目标描述、逐步脚本；如果 ProVerif 打出 `RESULT (but … is true.)`，一并告诉它，这表示只有一一对应被破、非单射认证仍然成立，也就是重放。原始长轨迹和 `model.pv` 通过分页工具按需读。

输出三块，和动画同步播放：

1. **开场一句**：场景给了攻击者什么。
2. **逐步说明**：每一步一句话，按步骤号对应。
3. **这一格的结论**：一两句，目标为什么因此被破。

**自动那批做完后，再开一次总结会话。** 它只读各格的结论，不读轨迹，写一段总结论：这些失败归结为哪几个问题、各涉及哪些格。超过上限时，注明还有几格待复现。

用户手动补做的格只生成它自己的结论，不自动改写总结；总结下方注明"另有 N 格为手动补做，未计入总结"，用户点"重新总结"才会纳入（见第 5 步）。

代码核对，不过就进修复轮：

- 逐步说明的步骤号与脚本一一对应，不多不少；
- 引号里的原文在轨迹或模型里逐字找得到；
- 总结里提到的格，都在已复现的列表里。

讲解语言跟随 `prompt_lang`，提示词写中英两版。

### 5. 前端

**流水线条**上加第 13 步"攻击"。

**攻击面板**放在结果矩阵下方，从上到下：

1. 计数：几个 false 格、几个已复现、几个待复现、几个在排队或正在复现、几个跳过。
2. 总结论。标题写明覆盖了几格。有手动补做、还没纳入总结的格时，下方注明数量，并给出"重新总结"按钮。
3. 已复现的格：每格一段动画，末尾是这一格的结论。
4. 待复现的格：带复选框的列表，顶部有"全选"。
5. 跳过的格：附原因。

**矩阵上的格子状态。** 颜色和图标双编码：

| 状态 | 样子 |
|---|---|
| 成立 | 勾号（格子底色照旧表示与 GT 是否一致） |
| false，待复现或跳过 | 叉号，和其他 false 格一样 |
| 排队中 | 主色虚线边，时钟 ◷ |
| 复现中 | 主色虚线框，呼吸闪烁，转圈 ⟳ |
| 已复现 | **左边一道 false 判定色的竖线**，记号同色，播放三角 ▶；底色仍表示与语料是否一致 |
| 已复现（手动补做） | 同上，右上角加一个小圆点 |
| 复现失败 | 右上角警示色角标，感叹号 |
| 已选中 | 在当前样子上加主色描边，复选框打勾 |

手动结果过期后（上游重跑、依据变了），格子回到"待复现"的样子，悬停提示"上次的复现已过期"。语料的 ⚔ 攻击徽章照旧叠加显示。

**矩阵上的交互。**

- 普通点击：已复现的格跳到它的动画；待复现的格在检查器里出现"复现这个攻击"按钮；其他状态在检查器里显示当前状态。
- 多选：工具条上有"多选"开关。打开后，点待复现的格子是加入或移出选择，不再打开检查器；它和面板列表里的复选框是同一个选择集。关掉开关就清空选择。选择只是页面上的临时状态，不进账本。
- 工具条上的"复现所选"按钮把选中的格子一次提交，按钮上写明格数和大约几次模型调用。没选任何格子时点它，就提示先去选择，不做成禁用按钮。
- 工具条上还有"停止"，队列里还有格子时生效。

**动画。** 控件有：回到开头、上一步、播放/暂停、下一步、当前步数，打开后自动播放一遍。每一步画出一支箭头，消息标签沿箭头移动过去；攻击者算出新消息的那一步，先在攻击者泳道上闪一下再发出。线的颜色和线型双编码：

| 线 | 含义 |
|---|---|
| 灰色细实线 | 正常发送 |
| 灰色虚线 | 攻击者原样转发 |
| 攻击者色细实线 | 攻击者递送它已经知道的值 |
| 攻击者色粗实线 | 攻击者算出的新消息 |

随当前步同步更新：当前步的说明和消息原文；"攻击者手里有"（新得到的值高亮，播完后被保护的秘密用判定色标出）；"各方以为"（每个诚实会话的起始参数，以及到当前步为止它通过的检查和记下的事件；播完后写出目标事件，并与对应的 begin 事件逐个参数对照，把不一致的参数标出）。

实现时的两处调整：脚本里没有"会话认为对端是谁"这个通用字段，所以"各方以为"显示的是会话自己记下的事实（检查行和事件），对端是谁由事件参数和起始参数说明；控制台的判定色里 false 是 `--v-neg`（紫），`--v-bad`（红）表示机器故障，所以已复现格子的深色实底和"目标被破"都用 `--v-neg` 一系。

**手动复现**照专家提问的写法：请求立刻返回，活在后台做，结果从事件流回来。

- `POST /api/runs/{name}/attacks`，请求体是 `{cells: [{scenario, goal}, …]}`。提交的格子进入这个 run 的复现队列。
- 队列每个 run 一条。重复提交的格子自动去重；队列没空时可以继续追加。按提交顺序做，第一版一次做一格，求解器和模型调用照常受现有并发闸约束。
- `POST /api/runs/{name}/attacks/stop`：清掉还没开始的格子，正在做的那格也取消，它们都回到待复现。
- 不做乐观更新：格子是"排队中""复现中"还是"已复现"，一律以事件为准。
- 回放模式下拒绝。run 还在跑时返回可读的 409，因为流水线自己的第 13 步还没结束。
- 求解器或模型没配置时，返回可读的错误，沿用开跑前的求解器检查。

实现时定下的几条细则（`orrery/nodes/reproduce_attacks/manual.py`、`orrery/api/attacks.py`）：

- 能手动提交的只有这一步留下的"待复现"格，以及手动补做后过期、复现失败或讲解没写成的格。这一步自己做的格要重做，就重跑这一步；跳过的格不能提交。
- 再次提交同一格时，上一次的文件整体移到 `superseded-<k>/`，不删除。停止时正在做的那一格也这样处理，所以它回到待复现，不会显示成"已复现但没有讲解"。
- 手动补做和重新总结的讲解语言跟随这个 run 自己记录的 `prompt_lang`，不跟随控制台当前的配置，保证同一个 run 的面板是一种语言。
- 过期判定：重新定位这一格当前的求解文件，路径和记录的不同，或者已经定位不到，就算过期。
- 手动会话的事件 `unit` 是它相对 run 根目录的路径（`_attacks/<场景>/<目标>`、`_attacks/summary`），控制台据此找到它的记录。

**重新总结**：

- `POST /api/runs/{name}/attacks/summary`：用全部已复现、且未过期的格子的结论，重写一份总结论。队列没空时返回 409，先等做完。
- 面板总是显示最新的一份总结，标题写明覆盖了几格。

**实现约束**（控制台规范）：

- 手写 SVG 加 `requestAnimationFrame`，不引动画库。
- 攻击者用单独的颜色 `--atk`，不借判定色；false 判定色只在"目标被破"那一刻出现。
- 已复现的格子只在左边加一道 `--v-neg` 竖线：底色要留给「与语料是否一致」，实底既盖掉了它，又比不一致的红更抢眼。
- 选中的描边用 Pico 主色，因为它是"可交互"的颜色，不与判定色混用。
- 消息原文、项名一律等宽字体。
- 遵守 `prefers-reduced-motion`：不做移动动画，只逐步显示。
- 长轨迹在面板内滚动，当前步自动滚到可见；步数超过绘制上限时明说没画的部分。
- 事件只带摘要；打开面板时再读结果文件，关掉就丢，不进 state。
- 界面文案走 i18n 字典；脚本里只存事实（`kind`、`from`、`to`），不存句子。

## 示例：NSPK，admission_open 场景

数据取自本地 run `NSPK24` 的真实轨迹，对应对话里给过的动画原型。逐步说明和结论是人写的示意，表示 AI 应该输出成什么样。这个 run 只有 3 个 false 格，全部自动做。

开场：admission = open，攻击者 I 以自己的身份在服务器 S 合法注册，A 可以正常选它做通话对象。

| # | 泳道 | kind | 消息 | 逐步说明 | 攻击者新知道 |
|---|---|---|---|---|---|
| 1 | A → 攻击者 | send | `(A, I)` | A 选 I 做通话对象，向 S 要 I 的公钥。这条请求被攻击者截下。 | |
| 2 | 攻击者 → A | inject | `sign((pk(I), I), SKas)` | 攻击者替 S 回答，递上 I 的证书。证书本来就公开，A 验证通过。 | |
| 3 | A → 攻击者 | send | `aenc((I_A, A), pk(I))` | A 用 I 的公钥加密随机数 I_A 发给 I。I 解开，拿到 I_A。 | `I_A` |
| 4 | 攻击者 → B | forge | `aenc((I_A, A), pk(B))` | 攻击者把同样的内容换成 B 的公钥重新加密，以 A 的名义发给 B。消息里只写了发送者，没写收件人。 | |
| 5 | B → S | send | `(B, A)` | B 以为 A 在找它，向 S 要 A 的公钥。 | |
| 6 | S → B | relay | `sign((pk(A), A), SKas)` | A 的证书经攻击者原样转到 B 手上。 | |
| 7 | B → A | relay | `aenc((I_A, I_B), pk(A))` | B 把 I_A 和自己的随机数 I_B 发给 A，攻击者原样转发。回复里没有 B 的名字。 | |
| 8 | A → 攻击者 | send | `aenc(I_B, pk(I))` | A 分不出这条回复不是 I 发的，照常把 I_B 发给 I。攻击者拿到 I_B。 | `I_B` |
| 9 | 攻击者 → B | forge | `aenc(I_B, pk(B))` | 攻击者再算一次，换成 B 的公钥重新加密，交给 B。 | |
| 10 | — | — | — | B 核对 I_B 无误，完成握手，认为自己在和 A 通话。 | |

各方以为：A 认为在和 I 通话（正确）；B 认为在和 A 通话（错误，实际是 I）。

这一格（secrecy_i_a）的结论：攻击者拿到了 I_A。根源在第 4 步和第 7 步：消息里只写了发送者，没写收件人，双方都无法察觉对方在和别人通话。

总结论（3 格）：三个失败是同一次攻击。攻击者以合法身份居中，把 A 发给它的消息改封给 B；因为消息不绑定收件人，B 以为在和 A 通话（auth_b_a_i_a），I_A 与 I_B 都落到攻击者手里（secrecy_i_a、secrecy_i_b）。

作为对照，ISO 9798-2 机制 6 的 K_AP 泄露场景（本地 run `ISO-9798-2-mechanism-6-mutual`，已核对轨迹）只有两步：A 向 P 发出带随机数 R_A 的请求；攻击者截下请求，自己挑一个会话密钥，用泄露的 K_AP 加密后冒充 P 回给 A，P 自始至终没有参与。开场一句"场景把 A 用来认 P 的密钥 K_AP 交给了攻击者"就已经说明了一切，不需要任何标签。

## 出错处理

这一步的问题分三类，只有后两类会让这一步失败。

**一、预期内的情况：按格记录，不算失败。** 原因写在对应格上，其他格照常生成。

| 情况 | 处理 |
|---|---|
| 长格式复现超时或超内存（大协议打印量很大） | 退回原来的短轨迹画图，标注"长格式复现超时" |
| 复现没有再次给出 false（按理不该发生，只多了一行打印设置） | 标注"复现未得到同样的攻击"，附两次输出 |
| 解析遇到不认识的轨迹行 | 不画动画，写明是哪一行，给原始轨迹链接 |

**二、框架 bug：显式报错。** 找不到给出 false 的 `02_`/`03_` 求解文件；复现运行报语法错误（那个文件已经解过一遍，只可能是我们加的那一行出了问题）；读不到上游产物。

**三、外部原因。** 模型接口出错（5xx、限流、网络、key 失效）；修复轮用尽；模型预算用尽。

两条设计减轻影响：

- 动画在讲解会话之前写好。讲解失败时动画照样能看，讲解位置显示失败原因。
- 一格的讲解失败不耽误其他格。全部做完后，再把失败的一起列出来。

**run 的状态：** 第二、三类出现在流水线的这一步时，这一步失败，run 记为 failed，和其他节点一致。此时前面各步都是 ok，判定本身不受影响；用 `--from-node reproduce_attacks` 只重跑这一步，讲解会话从断点续上。第一类不影响 run 的状态。

**手动复现失败**只在那一格上显示原因，不改变 run 的状态：它发生在 run 结束之后，不是流水线的一部分。

## 产物与事件

流水线这一步的产物在它自己的步骤目录里：

```
<NN>_reproduce_attacks/
  targets.json                 每个 false 格：自动做 / 待复现 / 跳过，以及原因
  <场景>/<目标>/trace.pv        复现运行的输入
  <场景>/<目标>/trace.txt       复现运行的输出（长格式）
  <场景>/<目标>/trace.dot       攻击图
  <场景>/<目标>/msc.json        逐步脚本
  <场景>/<目标>/transcript.jsonl 这一格的讲解会话
  summary/transcript.jsonl     总结会话
  attacks.json                 各格结论、总结论、待复现列表，前端读这个
```

手动补做的格写在 run 根目录的 `_attacks/<场景>/<目标>/` 下，文件同上；重新总结写在 `_attacks/summary/` 下，每次一份，前端读最新的。这沿用专家 `_review/` 的做法：run 结束后因为有人提问才产生的证据，不混进 run 自己的步骤目录。每份手动结果记下它依据的求解文件；流水线从上游重跑之后，依据变了的手动结果标为"已过期，可重新复现"。

事件新增两个：

- `AttackStatus`：一格的状态变了，带场景、目标和状态：`queued` 进入手动队列 / `running` 开始做 / `ok` 做完 / `failed` 失败（附原因）/ `cancelled` 被停止。流水线自动做的格没有 `queued`。前端按格折叠，状态量有界，一格一条。
- `AttacksSummarized`：手动触发的重新总结写完，带覆盖的格数。流水线第 13 步自己的总结不用这个事件，步骤结束（`NodeFinished`）就说明它已写完。

`running` 在动手之前发，遵守"先说再做"。两个事件都要同步登记到后端的已知类型表、前端的处理表和中英文案，契约测试会逐一比对。

配置新增 `attacks:` 一段，两个键：`enabled`（默认开）和 `auto_cells`（自动做的格数上限，默认 10）。跑批实验也用默认值，即开启；控制台的配置面板里可以直接改这两项。
